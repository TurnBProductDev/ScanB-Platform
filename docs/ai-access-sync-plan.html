ScanB platform · cross-repo plan · Web App + AI Bot

Add a user once, and ScanB AI knows them

Today a user who should reach the AI has to be added three times: in the Web App, in a JSON file in blob storage, and in a parquet file in blob storage. Then the bot has to be restarted. This plan makes the existing Add User screen the only step.

Why this is simpler than it looks

The AI's access file is already a copy of Web App data

The bot's row security comes from {container}/User_Security.parquet: one email, odsKey row per section a user can see. The Web App already stores the same thing in UserOdsMapping, set through the outlet → department → section picker admins use today.

Checked against UAT on 15 Sep

For every SB Mart user, the keys built from SQL as Outlet.LocationCode | Department.Name | Section.Name hash identically to that user's rows in the live parquet.

So the Web App already has everything the AI needs. The one fact it doesn't record is which blob container a customer's data lives in, and that's a single column.

Design decisions

The Web App decides, the bot writes the files

Web App SQL is the source of truth

Access is managed in one place. The two blobs become generated output, rebuilt from SQL on each change, so they can't drift. Hand edits stop being a normal workflow.

The bot owns its own files

Only the bot can clear its in-memory caches, and it already has pyarrow for parquet. The Web App stays on HTTP only (seam S1), needs no write access to agent-config, and gains no parquet dependency.

Admin calls use an app-only token

New /admin/* routes require an Azure AD app role, AI.Admin, which is granted only to the Web App's own identity. A signed-in person's token is refused, even a customer admin's.

Tenant moves must be explicit

If an email is already mapped to a different container, the write is refused unless the request sets allowMove. The Web App sets it only when the customer really changed. That boundary is where one customer could see another's data.

A failed sync never blocks the user

The SQL save and Azure AD invite still happen. The AI result is stored per user and shown as a status with a Retry. An AI outage slows AI access; it doesn't stop onboarding.

Removing access is part of the design

Deactivate and delete remove the user from both blobs. Today a deleted Web App user keeps a working AI mapping, a gap this closes.

Delivery

Four phases; each is useful on its own

Ordered so the reader of the files ships before the writer, as seam S1 requires. Estimates are for one developer and are rough.

1

Bot: no more restarts

  • Reload client_mapping.json when its ETag changes, checking at most every 60s. That's one metadata request, and it replaces the load-once-at-startup cache in db_manager.py.
  • Replace the lru_cache on get_user_allowed_keys with a 60s TTL cache that never caches a failed lookup. It used to cache "no access" until the next restart.
  • /auth/validate: an unmapped email returns authorized: false instead of an unhandled 500.
  • scripts/ai_users.py add | remove | show | diff: today's manual procedure as one command, with a snapshot, ETag guard and read-back check.

Bot: admin API

GET    /admin/ai-containers
GET    /admin/ai-users/{email}
PUT    /admin/ai-users/{email}        { container, name, odsKeys[], allowMove }
DELETE /admin/ai-users/{email}
PUT    /admin/ai-containers/{c}/users  { users[] }   # full customer resync
  • Each write is read → change → ETag-guarded upload, retried on a conflict and snapshotted first. It clears the local cache immediately; other replicas catch up within 60s through phase 1.
  • Validation: container must be on the allowlist; email is lower-cased; keys must match ^[^|]+\|[^|]+\|[^|]+$. A key the container's data doesn't contain is rejected.
  • An audit line per change goes to agent-config/audit/2026-09.jsonl: who, what, before and after key counts.
  • A resync reports users in the container who are missing from the request as notInRequest, and removes them only when the request sets removeMissing. A partial list can't revoke anyone by accident.
  • Authorization requires all four: the calling app in AI_ADMIN_CLIENT_IDS, an application token (any scp is refused), the AI.Admin role, and the tenant-pinned issuer check.

3

Web App: sync on Save

  • Migration (guarded, additive): Customer.aiContainer NVARCHAR(63) NULL, plus table AiAccessSync(userId, status, keyCount, syncedAt, error).
  • AiAccessSyncService runs after the SQL commit in AddNewUserAsync (Add and Edit), DeleteUsersAsync, the status toggle, and when a customer's AI flag or container changes.
  • It only acts when the customer has AI access and a container set; otherwise AI access is removed. Keys are built from UserOdsMappings, exactly as verified above.
  • Transport: the existing FastApi client (8s) with an app-only token. Routes live in config as FastApi:AiUsersPath and FastApi:AiContainersPath, following the pattern already in use.
  • UI: the status pill and Retry in the users grid, plus the container dropdown and Resync button on the customer screen.
  • Two rollout guards: nothing runs until FastApi:AiAccessSyncEnabled is on, and a customer with no aiContainer keeps its hand-made access untouched.
  • Resync always shows a preview first. Removing emails that aren't active users of the customer is a separate, unticked choice that lists each one.
  • Also fixes an existing bug: saving a customer opened through the list's Edit link turned ScanB AI off.

  • Later the same day: SB Mart's resync was applied from the UI, which proved the Web App's app token works. Two safety rules then shipped: an automatic save can't remove access the Web App didn't grant, and keys are checked by outlet against the customer's AI data, so brand-new customers work. CITYFLOWER and TurnB were then switched over as well; the rules keep their access unchanged until their outlet data is fixed and a resync is reviewed.
