Adding a customer to ScanB AI

A new customer in the Web App gets ScanB AI only after the AI has that customer's data. Work through these steps in order. Each one names the repo it touches and how to tell it's done.

One name, everywhere

Choose the customer's AI container name once (for example sb-mart): lowercase letters, digits and hyphens, 3–63 characters. The same string is the blob container, the runtime folder <name>-runtime, the bot's schema registry key, and the value an admin picks in the Web App's AI data container dropdown. A mismatch anywhere means the AI can't find the customer's data.

The steps

  1. Create the storage container and load the source data

    • Create blob container <name> in the AI storage account.
    • Upload the customer's source CSV exports to the container root. The build job reads only root-level CSVs.

    Done when the container lists the CSVs at its root.

    WhereAzure Storage
    UAT / prodturnbtestblobstorage / scanbaiagent

  2. Register the customer in the AI Bot's code

    • pipeline_runner.py, build_vector_index.py, generate_master_entity_dataset.py: add a CLIENT_CONFIGS entry. runtime_dir must be <name>-runtime. If the Power BI model has the same shape as an existing customer's, reuse its ingest script, as SB Mart reuses cf_kg_injest.py.
    • schemas/<name>.py, plus the _REGISTRY entry in schemas/__init__.py. This is what makes the container selectable and grantable.
    • The file maps in graph_retriever.py (graph, vector index) and hybrid_resolver.py (entity master, vector index).
    • Optional: "_clients" on customer-specific business rules; an ENTITY_DB entry in evals/run_eval.py.

    Done when .venv/Scripts/python -m pytest -m unit -q passes.

    RepoScanB-AI-Agent
    WhoDeveloper

  3. Build the customer's AI data

    • Run the pipeline job with the customer added to PIPELINE_CLIENTS. It builds the knowledge graph, vector index and entity master, and publishes them to the file share under <name>-runtime/.
    • Check the entity master's outlet codes: these are the codes the Web App's outlet import must use in step 7.

    Done when <name>-runtime/ holds the graph folder, the vector index and a readable *_entity_master.db.

    WherePipeline container job → file share
    Why it mattersNo entity master means no access can be granted (see guardrails)

  4. Deploy the AI Bot

    • Follow the deploy-bot-uat skill: preflight, build, image gate, push, release, smoke.
    • Add the customer to PREWARM_CLIENTS if its first question shouldn't pay the cold-start cost.

    Done when the new revision is Healthy and the customer's Details page in the Web App lists <name> in the AI data container dropdown.

    RepoScanB-AI-Agent
    AppUAT scanb-ai-agent · prod scanbaiagent

  5. Set up daily insights and report summaries Optional

    • Onboard the client in Auto-Insight's config wizard (Connect → Probe → Configure → Author → Deploy). Set ai_content_client to <name>.
    • Without this, the AI chat works, but the Web App shows sample insights and summaries for this customer.

    Done when <name>/ai-content/kpi/client/insights.json exists after a run.

    RepoAuto-Insight-Generation
    Docsdocs/config-ui.md

  6. Create the customer in the Web App

    • Customers → Add: name, email domains, user limit. Roles are created automatically.
    • Reports tab: bind each Power BI report (its report id is also the AI summary's file name).

    Done when the customer's Details and Reports tabs are complete.

    WhereWeb App, as product admin

  7. Import outlets using the AI data's outlet codes

    • Outlets tab → import the outlet, department and section workbook.
    • Outlet codes must match the AI data exactly: the Web App builds each access key as LOCATIONCODE|DEPARTMENT|SECTION. Import every outlet the customer's users should see.

    Done when the outlet list matches the entity master's outlet codes from step 3.

    WhereWeb App, as product admin
    What goes wrongTurnB on UAT: MH10 in the Web App, ST1 in the AI data

  8. Add users, then switch ScanB AI on

    • Users tab → add users with their outlets, departments and sections. Each one gets an Azure AD guest invite.
    • Details → Edit: set ScanB AI to Enable and the AI data container to <name>. Save.
    • The resync preview opens on its own. Review who will get access, then Apply.

    Done when the Users tab shows Synced · N sections for every user, and one of them can ask the AI a question.

    WhereWeb App, as product admin
    From then onAdding, editing, deactivating or deleting a user updates their AI access automatically

Guardrails that catch mistakes

Refusals change nothing. The user's row in the Users list shows the reason.

SituationWhat happensWhat to do
The AI has no data for the customerEvery grant is refused: "The AI has no data for this customer yet"Finish steps 3–4
A user's outlet isn't in the AI dataRefused, naming the outletsFix the outlet codes (step 7)
A save would remove AI access the Web App didn't grantRefused: "would remove N of M sections"Product admin: Details → Resync, review, Apply
The email already has AI access under another customerRefused as a tenant moveResolve which customer the person belongs to
Customer has no AI data container setThe Web App leaves its users' AI access untouchedSet the container when the data is ready
AI service unreachableThe user save still succeeds; AI status shows FailedRetry on the user's row
Worth fixing

Step 2 touches six files because each module keeps its own customer map. A single customer registry in the AI Bot, read by the pipeline, schemas, retriever and resolver, would make adding a customer's code a one-file change and remove the chance of a missed map.
