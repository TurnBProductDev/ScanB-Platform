A question becomes an answer in ten stages

02 · The assistant09

Why a graph, and not just SQL

Retail questions are questions about relationships: this SKU, in that store, in this brand, over that period, against its peers. Cheap on a graph, expensive on wide tables.

Kuzu · the facts

Knowledge graph

Stores, products, brands, categories, suppliers — and the sales and stock relationships between them. This is what the generated query actually runs against.

FAISS · the meaning

Vector index

Maps what a person typed to what the data calls it. "Fresh chicken", "FRESH CHICKEN & PARTS" and a SKU code all have to land on the same thing.

DuckDB · the names

Entity master

Every real name and alias, for exact lookup. Tried first, because it is both faster and more certain than a similarity search.

Resolution runs in that order — exact, then alias, then meaning. If it still can't tell which of two things you meant, it asks. It does not guess and it does not silently pick one.

02 · The assistant10

Three stages exist only to stop a confident wrong answer

Before it runs

The validator

Reads the generated query and checks every table and column it names against the graph's real schema. A query referencing something that doesn't exist goes back to be rewritten — with the error text attached — up to three times.

Before it runs

The enforcer

Rewrites the query to include that user's data-scope keys — recursively, including inside sub-queries, unions and optional matches, which is exactly where a naive implementation leaks. Anything that would write, change or delete is blocked outright.

After it runs

The verifier

Compares every figure in the written answer against the rows that came back. "Zero because the data says zero" is reported differently from "zero because your permissions excluded it".

Every question also leaves a full trace — each stage, each model call, timings and token counts — retained for review and automatically deleted after 30 days.

02 · The assistant11

Deeper questions need more than one query In development

"Which sections are falling short, and why?" cannot be answered by a single lookup. The planning path decomposes it, runs the steps, then checks whether the plan actually answered the question.

Step 1

Plan

Break the question into ordered, individually answerable steps.

Step 2

Execute

Run each step through the same validated, permission-enforced path — plus a sandboxed calculator and a deterministic business-rule lookup.

Step 3

Review

Measure how much of the original goal the evidence actually covers. Revise the plan if it falls short.

Step 4

Synthesise

Turn the collected evidence into one answer with a stated verdict.

Built and unit-tested behind a feature switch. It is being measured against the answer-quality benchmark before it is turned on — the same standard every other change is held to.

SECTION THREE

The agent that writes its own queries

Nobody picks a KPI, writes a DAX measure or fills in a template. It inspects the customer's model, works out what it can measure, and decides what deserves a manager's attention today.

03 · The generator13

One run, two products, two branches at once

03 · The generator14

It is not given a query library

  • It reads the model's metadata first — which measures exist, which hierarchy this particular business uses, what this report is for. Division, department, section, category are discovered, not assumed.
  • It plans what it wants to know as plain intents, then generates the DAX for each one.
  • Every generated query is checked against the real model before it runs. If Power BI still returns an error, the exact error text is fed back once for a repair attempt — a failed query is repaired, not silently dropped.
  • Queries are budgeted. A run has a fixed allowance of calls, spent on the highest-value scans first, so cost and runtime stay predictable.

This is what makes onboarding a new customer configuration rather than development. Point it at a different semantic model and it discovers that business's own shape instead of expecting the last customer's.

03 · The generator15

The hard part is relevance

Rank by percentage and the report leads with a category worth a rounding error moving 2,000%. Ranking blends three things instead.

40%
Impact — how much of the total business the move actually represents
35%
Magnitude — the size of the move, capped so a freak percentage can't dominate
25%
Unexpectedness — how far it deviates from how the rest of the estate moved
100%
Coverage — every member of every level still gets a ranked line, so nothing is silently omitted

A headline also has to clear a minimum relevance floor. The narrative is selective; the coverage is complete — which is how you get a short report that nobody has to distrust.

03 · The generator16

A daily report that repeats itself stops being read

Memory

It knows what it already told you

The agent keeps a record of what it has delivered and suppresses a finding that overlaps a recent one — measured on the facts in the story, not just its title.

A story that has already run cools down before it can lead again.

Overrides

Unless something genuinely changed

Three things jump the rotation: a reversal in direction, a newly completed week, month or quarter, and a move large enough in both size and share to matter regardless.

If everything overlaps, the best story still ships rather than the page going silent.

There is also a calendar check: if every area moves the same way at once, suspect the comparison period before declaring a bad month — and the caveat names the areas it does not explain, so it can't be used as a blanket excuse.

Code owns the arithmetic. The model owns the language.

04 · Trust19

What the validators actually reject

Real rules, enforced in code on every generated page. Not prompt instructions — checks that fail a build.

  • A figure quoted in the prose that doesn't appear in the data behind the page — including one quoted to more decimal places than allowed.
  • A stated cause that the data only shows as correlation.
  • Calling partial evidence a complete share of total.
  • Naming an area as included in year-on-year growth when it was excluded from the comparison.
  • Internal vocabulary leaking into a manager-facing page — or a month rendered as "month 1" instead of January.
  • Calling the transaction count "footfall" or "visits". It is bills, not people, and the difference changes what a manager does next.
  • Running the same sentence template across the page — caught proportionately, so two areas legitimately sharing a situation don't fail a correct page.

And the whole thing is deterministic: the same inputs must produce the same page. The build gate re-derives real artifacts from committed inputs and compares byte for byte, so a change that moves a number anywhere fails with a field-level diff.

05 · Security20

Can another customer see my data? Can my own staff see too much?

05 · Security21

The gates a single request passes

Who you areMicrosoft Entra ID against the customer's own directory. No passwords stored; their MFA and conditional-access policies apply unchanged.
Whose data you reachThe email inside the validated token maps to exactly one container. Nothing in the request body can influence which.
Which rows you reachThe query is rewritten with that user's data-scope keys before it runs. Deny by default — a query that can't be proven secure is refused, not run.
Which reports you reachEntitlements set by an administrator; Power BI embed tokens minted per user, per report, short-lived.
What can be addressedReport ids must be well-formed GUIDs and dates must be real calendar dates — both become storage path segments, so these are path-traversal guards.
What is publicStatic files are served before authentication, so customer data is kept out of the public folder entirely and dashboards are served only through an authenticated, entitlement-checked route.
05 · Azure22

All of it inside Azure

No third-party AI service, no external warehouse, no data leaving the tenant boundary in normal operation.

Identity

Entra ID

Separate app registrations for the web app and the API with a dedicated scope. Scheduled automation runs as a managed identity — no stored credential to leak.

Compute

Container Apps

The API scales with demand. Container Apps Jobs run the nightly insight generation, one per customer, and the knowledge-graph builder. A VM with IIS hosts the web app.

AI

Azure OpenAI

Three deployments used by tier — a strong reasoning model, a fast inexpensive one for routing, and an embedding model. Prompts stay inside the service.

Data

Blob, Files, SQL

One blob container per customer. Azure Files holds the built graph and indexes. SQL Server holds only app configuration — no customer transaction data.

Analytics

Power BI / Fabric

The semantic models the generator reads and the reports the web app embeds. Read and build permission only — it never writes to the model.

Operations

Automation

Scheduled runbooks pause analytics capacity outside working hours — a material line on the monthly bill. Storage lifecycle rules expire diagnostic traces automatically.

Three things worth remembering

Your Power BI stays where it is. We add an AI layer that writes your analysis overnight and answers questions during the day — inside your own Microsoft tenant.

The AI never does the maths

It receives numbers that are already correct and turns them into English — and a validator checks that English back against the numbers before anyone sees it.

Isolation is structural

Your own container, your own graph. And inside your business, the assistant can only query rows that person is already entitled to — because the query is rewritten before it runs, not filtered afterwards.
