01

What ScanB is

ScanB is an AI analytics platform for retailers. A retailer's data already sits in Power BI. ScanB puts a product around it that answers questions, and one that raises them.

A store manager signs in with their normal work account and gets three things in one place:

  • The reports they already know — their Power BI reports, embedded, with the access rules their business already has.
  • Analysis nobody had to ask for — every morning, written overnight: what moved, by how much, and why it probably moved.
  • An assistant they can just ask — "which branches are below target this week?" — in plain English, answered from their own data.

Behind that are three independently developed systems. They ship as one product but share no code — they talk to each other only over HTTPS and shared storage, which is what lets each one be worked on, tested and released without waiting for the other two.

Say it like this

"Your Power BI stays where it is. We put an AI layer on top of it that writes your analysis overnight and answers questions during the day — inside your own Microsoft tenant."

04

The agent that answers

A question in plain English becomes a database query, gets restricted to what that user may see, runs against a retail knowledge graph, and comes back checked.

The assistant is not a single prompt to a language model. It is a state machine with ten defined stages, each of which can fail safely and hand control somewhere sensible. Some stages use a model; most do not.

What it queries, and why a graph

Retail questions are questions about relationships: this SKU, in that store, in this brand, over that period, compared with its peers. Those are cheap to answer on a graph and expensive to answer on wide tables. So each customer's data is loaded into three complementary stores:

  • A knowledge graph (Kuzu) holding stores, products, brands, categories, suppliers and the sales and stock relationships between them — this is what the generated query actually runs against.
  • A vector index (FAISS) that maps what a person typed to what the data actually calls it. "Fresh chicken", "FRESH CHICKEN & PARTS" and a SKU code all need to resolve to the same thing.
  • An entity master (DuckDB) for exact and alias lookups, tried first because it is both faster and more certain than a similarity search.

Resolution runs those in order — exact, then alias, then meaning. If it still cannot tell which of two things the user meant, it asks rather than guesses.

The stages that stop bad answers

Three of the ten stages exist only to prevent a confident wrong answer:

  • The validator reads the generated query and checks every table and column it mentions against the graph's real schema before it runs. A query naming something that does not exist is sent back to be rewritten, with the error text attached, up to three times.
  • The enforcer rewrites the query to include the signed-in user's data-scope keys, recursively — including inside sub-queries, unions and optional matches, which is where a naive implementation leaks. It also blocks anything that would create, change or delete data.
  • The verifier compares every figure in the written answer against the rows that came back. Zero rows because the data says zero is reported differently from zero rows because the user's permissions excluded them.

Every question also leaves a full trace — each stage, each model call, timings and token counts — stored for review and automatically deleted after 30 days.

Say it like this

"It doesn't ask an AI what your numbers are. It uses AI to write a database query, checks that query against your real schema, restricts it to what that person is allowed to see, runs it, and then checks the written answer back against the rows that came out."

05

The agent that reports

Nobody writes a query, picks a KPI or fills in a template. The agent inspects the customer's Power BI model, works out what it can measure, writes its own DAX, and decides what is worth a manager's attention today.

It runs unattended overnight. Each run produces two things at once, from two branches that execute concurrently: a descriptive report of what the numbers are, and an investigative report of why they look that way.

It writes its own queries

The agent is not given a query library. It reads the model's metadata, plans what it wants to know as plain intents, and generates the DAX for each one. Every generated query is checked against the real model before it runs — and if Power BI still returns an error, the exact error text is fed back once for a repair attempt rather than the query being silently dropped.

This is what makes onboarding a new customer configuration rather than development. Point it at a different semantic model and it discovers that business's own hierarchy — division, department, section, category — rather than expecting the one the last customer used.

It decides what is worth saying

The hard part of an unprompted report is relevance. A naive ranking leads with whatever moved the largest percentage, which is almost always something trivial — a category worth a rounding error can move 2,000% and mean nothing. So ranking blends three things: impact (how much of the total business the move represents), magnitude (the size of the move, capped), and unexpectedness (how far it deviates from how the rest of the estate moved). A headline also has to clear a minimum relevance floor.

Alongside that, the report gives every member of every level a ranked line, so nothing is silently omitted — the narrative is selective, the coverage is complete.

It remembers what it already told you

A daily report that repeats yesterday's story stops being read. The agent keeps a memory of what it has delivered and suppresses a finding that overlaps a recent one — unless something genuinely changed: a reversal in direction, a newly completed week or month, or a move large enough in both size and share to override the rotation.

What it publishes

  • A written summary of the period, leading with overall performance, then the business areas that earned narrative.
  • An interactive four-layer dashboard — Overview, Entities, Areas, Detail — in two time views, with a revenue decomposition into transactions × basket size × price, red/amber/green bands per measure, and a calendar check that flags when a whole-estate move looks like a comparison artefact rather than a bad period.
  • A KPI feed of insight and alert cards for the hub.
  • A dated archive, so any past day's analysis can be reread exactly as it was published.
Say it like this

"Every night it looks at your whole business, ranks what actually matters — not just what moved the most — writes it up with the evidence behind it, and remembers what it told you yesterday so it doesn't repeat itself."

06

Why it isn't a chatbot on a database

This is the question every technical evaluator asks. The answer is a rule we apply everywhere: code owns the arithmetic and the structure; the language model owns only the language.

A model that is asked to both calculate and narrate will produce a fluent number that is wrong. So it is never asked to. Every figure that reaches a customer was computed in Python or by the database. The model's job is to turn already-correct figures into readable prose — and then a validator checks that it did.

What the validators actually reject

These are real rules, enforced in code on every generated page:

  • A figure quoted in the prose that does not appear in the underlying data model — including one quoted to more decimal places than the page permits.
  • A stated cause that the data only shows as correlation.
  • Calling partial evidence a complete share of total.
  • Naming a business area as included in year-on-year growth when it was excluded from the comparison.
  • Internal vocabulary leaking into a manager-facing page — a technical population term, or a month rendered as "month 1" instead of January.
  • Calling the transaction count "footfall" or "visits". It is bills, not people, and the distinction changes what a manager does next.
  • Running the same sentence template across the page, when the page really is saying the same thing about everything.

On the assistant side, the equivalent guard is the numeric grounding check on every answer, plus the schema validator that refuses to run a query naming a column that does not exist.

The other thing evaluators ask

Determinism. The same inputs must produce the same page — otherwise nothing is testable. So the arithmetic, ranking, banding and layout are all pure functions with no model in the loop, and the build gate re-derives real artifacts from committed inputs and compares them byte for byte. A change that alters a number anywhere fails the build with a field-level diff.

Say it like this

"The AI never does the maths. It gets numbers that are already correct and turns them into English — and then we check the English against the numbers before anyone sees it."

07

Running on Azure

Everything runs inside Microsoft Azure. There is no third-party AI service, no external data warehouse and no data leaving the tenant boundary in the course of normal operation.

Identity

Microsoft Entra ID for user sign-in and for service-to-service authorisation. Separate app registrations for the web application and the API, with a dedicated API scope, so a token minted for one cannot be replayed against the other.

Managed identities for scheduled automation — no credential is stored anywhere for those jobs to leak.

Compute

Azure Container Apps hosts the AI API, scaling with demand.

Container Apps Jobs run the two unattended workloads: the nightly insight generation, one job per customer, and the knowledge-graph builder.

Azure Virtual Machine with IIS hosts the web application.

AI

Azure OpenAI, in the customer's region, with three deployments used by tier: a strong reasoning model for query generation and analysis, a fast inexpensive model for classification and routing, and an embedding model for entity resolution. Prompts and completions stay within the Azure OpenAI service.

Data

Azure Blob Storage — one container per customer, holding published AI content, chat sessions, generated charts, dashboard assets and diagnostic traces.

Azure Files — the built graph, vector index and entity master, mounted by the API at runtime.

SQL Server — the application's own configuration: users, reports, modules, dashboards and entitlements. No customer transaction data lives here.

Analytics

Power BI / Microsoft Fabric capacity — the semantic models the generator reads and the reports the web application embeds. Read and build permission on the dataset is all the agent needs; it never writes to the model.

Operations

Azure Automation with scheduled runbooks pauses the analytics capacity outside working hours, which is a material line item on the monthly bill.

Blob lifecycle policies expire diagnostic traces automatically, so retention is enforced by the platform rather than by a job that someone has to remember to run.

Deployment is per repository and independent: the API and the generator ship as containers; the web application is packaged, transferred over a short-lived signed URL and swapped in by rename, so a release takes the site down for seconds rather than the length of a file copy, and rolling back is a rename in the other direction.

08

Data security

Two questions matter to a prospect: can another customer see my data, and can my own staff see more than they should? The answers are enforced in different places, and neither depends on the AI behaving well.

One customer, one container

Tenant separation is physical, not a column in a shared table. Each customer has their own storage container, their own knowledge graph, their own vector index and their own entity master. There is no code path that resolves a signed-in user to more than one container — a request either resolves to exactly one, or it fails.

The gates a request passes

Who you are

Sign-in is Microsoft Entra ID against the customer's own directory. ScanB stores no passwords, and the customer's existing MFA and conditional-access policies apply unchanged. Every API call carries a per-user token scoped specifically to this API.

Whose data you reach

The email inside the validated token is mapped to exactly one storage container. Nothing in the request can influence which container is chosen.

Which rows you reach

Before a generated query runs, it is rewritten to include the signed-in user's data-scope keys — recursively, including inside sub-queries, unions and optional matches. Deny by default: a query the enforcer cannot prove it has secured is refused rather than run. Anything that would create, change or delete data is blocked outright; the agent has read access only.

Which reports you reach

Report and module entitlements live in the configuration database and are applied by an administrator. Power BI embed tokens are minted per user, per report, with a limited lifetime.

What can be addressed

Report identifiers must be well-formed GUIDs and dates must be real calendar dates, because both become segments of a storage path — these are path-traversal guards, not input tidiness. A request for a specific past date never silently falls back to today's content, which would show current numbers under an old label.

What is public

In the web application, static files are served before authentication runs. That is a deliberate, documented boundary: customer data is kept out of the public folder entirely, and dashboard assets live outside it and are reachable only through an authenticated route that also checks entitlement.

Secrets and retention

Credentials live in environment secrets and untracked configuration, never in source control, and are never carried between environments — a deployment refuses to overwrite the target's own configuration. Scheduled automation runs as a managed identity with no stored credential. Diagnostic traces expire automatically after 30 days, and can be captured with all prompt and response text redacted at the point of storage while keeping timings and structure for debugging.

And it is tested as security, not as features

The permission rewriting has its own regression suite, covering the bypass shapes that defeat a naive implementation — unions, nested sub-queries, optional matches, variable-length relationships and missing aliases. Session isolation has its own tests. A separate integrity gate checks the built graph against what the query prompts assume, because the failure that matters most is silent drift: a permission key that stops being written during a rebuild would turn a secured relationship into an unsecured one without any error appearing.

A second, structure-aware permission engine runs alongside the production one in shadow mode, comparing decisions on live traffic without affecting them In development. A deliberate refusal from it is never overridden.

Say it like this

"Your data sits in your own storage container with your own graph — not a shared table with a customer column. And inside your business, the AI can only ever query the rows that person is already entitled to, because we rewrite the query before it runs rather than filtering results afterwards."

Each repository has its own gate, and all three can be run together from one command before anything ships.

Auto-InsightArtifact audit, after every live runRe-checks a delivered page: that the decomposition sums, the waterfall closes, every percentage matches its own values, and every claim in the prose is grounded.

Answer quality is measured, not assumed

The assistant has a benchmark of 105 real retail questions spanning inventory, procurement, sales, pricing, operations and executive-level asks. The harness runs the actual pipeline — no mocks — and records the final answer, the query that produced it, the rows that came back, the entities it resolved, retries and latency for every question. Scoring combines deterministic checks with an optional model-graded rubric. That is how a change to prompts or resolution is shown to be an improvement rather than assumed to be one.

Onboarding a new customer

There is an internal console for bringing on a new customer: configure them, probe their semantic model without running any AI or writing anything, review what the probe found, then deploy their nightly job. The probe step matters — it is where a model's shape problems surface cheaply, before a full run. Where a customer's model is missing something a feature needs, that becomes a recorded configuration decision rather than a code change.

Glossary

For when a prospect asks what a word on this page means.

Semantic model
The Power BI layer that turns raw tables into business measures — "revenue", "units", "bills" — with the relationships between them. The generator reads this, not the raw database.
DAX
The query language for a Power BI semantic model. The agent writes it; no one on the customer's side ever does.
Knowledge graph
A database that stores things and the links between them rather than rows in tables. Fast at "which suppliers serve stores that are underperforming", which is most retail questions.
Cypher
The query language for that graph — the assistant's equivalent of DAX.
Vector index
A search index over meaning rather than spelling. It is how "fresh chicken" finds the category the data actually calls something else.
LangGraph
The framework both agents are built on. It makes an agent an explicit graph of stages with defined transitions, rather than a loop that decides what to do next each time — which is what makes the behaviour testable.
Row-level security
Restricting which records a person can see. Here it is applied by rewriting the query before it runs, not by filtering results after.
Embed token
A short-lived credential that lets one specific user view one specific Power BI report inside ScanB.
RAG band
Red / amber / green. In the briefing, applied per measure against the standard that measure is held to — a decline in units is judged more harshly than a decline in revenue, because it means real demand fell.
Three-lever split
Revenue = transactions × basket size × price. Separating the three tells a manager whether they had fewer trips, smaller baskets or lower prices — which have opposite responses.
